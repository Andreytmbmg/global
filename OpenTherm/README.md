# Регулировка температуры комфорта OpenTherm — Глобальный

Глобальный JS-сценарий (SprutHub, Nashorn/ES5+) для погодозависимого регулирования
температуры теплоносителя OpenTherm-котла с учётом температуры по комнатам, окон,
вентиляции, тёплых полов и присутствия жильцов. Раз в 30 минут считает новую
температуру теплоносителя и шлёт подробный отчёт в Telegram.

## Как это запускается

Сам файл только объявляет функцию `global.adjust_heating()` — она ничего не делает
при загрузке сценария. Запускает её отдельный BLOCK-сценарий **"Обновление OpenTherm"**:

- по cron `0 0/30 * ? * * *` (каждые полчаса) с задержкой 11 сек;
- дополнительно при возврате любого аксессуара онлайн (`AccessoryInformation.C_Online`),
  чтобы пересчитать сразу после сбоя связи, не дожидаясь следующего получасового тика.

## Связанные сценарии

Эти сценарии не входят в этот файл, но без них часть логики работает не так, как
задумано — они взаимодействуют с этим сценарием через общие аксессуары/термостаты:

| Сценарий | Что делает |
|---|---|
| **Обновление OpenTherm** | Триггерит `global.adjust_heating()` раз в 30 минут и при восстановлении связи с аксессуарами |
| **Погода Yr.no** | Раз в 30 минут опрашивает `api.met.no`, кладёт результат в `global.yr` — fallback-источник погоды, когда метеостанция WS90 недоступна |
| **Виртуальные термостаты по комнатам** | Выставляет `targetTemp` термостатов по времени суток (день/ночь), когда кто-то дома |
| **Дома не дома** | По `SecuritySystemCurrentState` (взведена/снята охрана) переключает `targetTemp` термостатов между "эконом" (23°C) и "комфорт" (24–25°C) при отсутствии/присутствии всех жильцов |
| **Зима лето** | По уличной температуре с гистерезисом переключает систему между режимами отопления/лета, деактивирует термостаты и обогрев летом |

## Конфигурация комнат (ROOM_CONFIG)

Все ID аксессуаров/сервисов/характеристик по комнатам собраны в одном объекте
`ROOM_CONFIG` в начале файла. Формат троек — `[accId, svcId, chId]`, который
напрямую скармливается в `safeGetValue()`. Чтобы добавить или изменить комнату —
правится только этот объект, остальной код ничего не знает про конкретные ID.

```js
"Спальня": {
    targetTemp: [488, 13, 18],   // термостат: целевая температура комнаты
    sensor: [428, 13, 15],       // датчик: текущая температура комнаты
    windows: [[370, 13, 15]],    // массив окон — открыто/закрыто
    ventilation: [268, 13, 15],  // датчик вентиляции; null = вентиляции в комнате нет
    floorHeating: [479, 22, 24], // контур тёплого пола (вкл/выкл)
    radiators: [[303, 13, 15]],  // массив радиаторов — греет/не греет
    airQuality: { acc: 249, svc: 27, ch: 30, type: "CO₂", unit: "ppm" } // null = нет датчика
}
```

Сейчас настроено 4 комнаты: Спальня, Детская, Гост-ая, Кухня 🍽️.
Датчик вентиляции физически есть только в Спальне и Гост-ой (в Детской и на Кухне
соответствующее поле — `null`, что означает «не подключено в сценарии», а не
«вентиляции физически нет» — если появится датчик, достаточно подставить его ID).

## Источники погоды и fallback-цепочка

Для `outsideTemp`, `uvIndex`, `windSpeed` сценарий сначала пытается прочитать
значение с реальной метеостанции **WS90** (accessory 537), и только если датчик
недоступен — берёт значение из `global.yr` (заполняется отдельным сценарием
"Погода Yr.no" из api.met.no), а если и там пусто — из `global.lastExternalData`
(последнее успешно полученное значение, персистентное между запусками).

```
safeGetValue(WS90) → доступен? → используем его
                   → недоступен → global.yr.<field> → доступен? → используем
                                                      → недоступен → global.lastExternalData.<field>
```

`forecastTemp` (прогноз на 6 часов) и `cloudiness` (облачность) берутся только из
`global.yr`/`global.lastExternalData` — у WS90 нет собственного прогноза.
`weatherCondition` (текстовое описание — "Солнечно", "Облачно" и т.п.) сначала
читается с WS90, при отсутствии — берётся `global.yr.condition_1_hour`.

## Присутствие жильцов

```js
var presenceSensors = [
    { accId: 535, svcId: 17, chId: 19, name: "Олеся",   emoji: "👱🏼‍♀️" },
    { accId: 535, svcId: 13, chId: 15, name: "Андрей",  emoji: "🧔🏻‍♂️" },
    { accId: 535, svcId: 21, chId: 23, name: "Кристина", emoji: "👧" }
];
```

Для каждого жильца с `HC.OccupancyDetected === 1` в сообщение добавляется его
эмодзи. Это информационный блок — на фактическую коррекцию отопления присутствие
не влияет: понижение целевых температур при отсутствии всех жильцов уже делает
отдельный сценарий "Дома не дома" через `targetTemp` термостатов.

## Индикаторы котла и насоса тёплого пола

- `isBoilerOn()` — accessory 275/13/15 (`HS.*`, bool), эмодзи ✅/❌ сразу после
  значения базовой температуры теплоносителя.
- `isFloorPumpOn()` — accessory 114/13/15 (`HS.Outlet` → `HC.On`, bool), эмодзи
  🔄 (включен) / 🚫 (выключен), идёт сразу после индикатора котла.

## Алгоритм расчёта температуры теплоносителя

1. **Базовая температура по отопительной кривой**:
   `baseWaterTemp = 53 + (0 − outsideTemp)` — чем холоднее на улице, тем выше
   базовая температура теплоносителя (точка отсчёта: 53°C при 0°C на улице).
2. **Коррекция на прогноз** — если через 6 часов станет холоднее/теплее,
   `(forecastTemp − outsideTemp) / 2` подмешивается заранее, чтобы не запаздывать.
3. **Коррекция на ветер** — усиливает теплопотери: +1°C при 3–6 м/с, +2°C при
   6–9 м/с, +3°C при ≥10 м/с.
4. **Коррекция на УФ/облачность** — солнечный прогрев снижает требуемую
   температуру теплоносителя (от −1 до −5°C в зависимости от интенсивности УФ
   и степени открытости неба).
5. Итог ограничивается диапазоном **40–80°C**.
6. По всем комнатам (кроме игнорируемых — открыто окно или работает вентиляция)
   находится **самая холодная** (`getColdestRoom`) — с наибольшим положительным
   `target − sensor`. Если таких нет (все прогреты/игнорируются) — берётся
   «наименее перегретая» из неигнорируемых, что обычно приводит к сбросу на
   базовую температуру (см. ниже).
7. `minDelta = target − sensor` для выбранной комнаты, с округлением до 0.1°C.
8. К `minDelta` применяется эскалация по стабильности (см. следующий раздел).
9. `correctionFactor` зависит от величины отклонения: 2 (|Δ|≤1), 2.5 (1<|Δ|≤2),
   3 (|Δ|>2) — чем сильнее отклонение, тем агрессивнее коррекция.
10. `newWaterTemp = baseWaterTemp + minDelta × correctionFactor`, округляется.
11. **Защита от перегрева**: если выбранная комната уже перегрета (Δ<0) —
    теплоноситель не повышается, может только понижаться.
12. **Сброс на базовую**: если `-0.2 ≤ minDelta ≤ 0.2` (комната практически на
    цели) — `newWaterTemp` принудительно равен `baseWaterTemp`.
13. Две защиты от «залипания» вопреки направлению тренда: если стабильно жарко
    (`stableHotRoomCount ≥ 3`), но расчёт почему-то предлагает повысить —
    принудительно понижаем на 1°C; и симметрично для стабильного холода.
14. Финальное ограничение 40–80°C, запись в аксессуар 275/13/18.

## Стабильность: эскалация холодной/горячей комнаты

Чтобы не реагировать слишком резко на разовые колебания в 0.2°C (отопление имеет
большую тепловую инерцию — реакция на изменение температуры занимает часы, а не
минуты), ведутся счётчики `stableColdRoomCount` / `stableHotRoomCount`:

- Пока **самая холодная комната не меняется** — счётчик растёт шагом **+2** за
  каждый 30-минутный прогон (пока отклонение сохраняет знак).
- При **смене самой холодной комнаты** — счётчик сбрасывается, но не теряет
  текущее измерение: стартует заново с **+1** для новой комнаты.
- В «мёртвой зоне» (`-0.2…0.2`) — счётчик обнуляется.

Эскалация по накопленному счётчику (действует на `minDelta`, а не напрямую
на температуру):

| Счётчик | Коррекция `minDelta` |
|---|---|
| ≥3 | ±1°C |
| ≥4 | ±1.5°C |
| ≥5 | ±2°C |

Поскольку шаг счётчика равен 2 (при неизменной комнате), типичная
последовательность — 1→3→5 (после смены комнаты), т.е. ступень "≥4" обычно
проскакивается, что сохраняет прежнее (уже протестированное на практике)
поведение сценария.

## ПИ-регулятор (теневой тест)

Ступенчатая эскалация выше — по сути, грубая ручная имитация интегральной
составляющей классического ПИ-регулятора. Чтобы изучить, даст ли полноценный
ПИ более гладкое и предсказуемое поведение, в сценарий добавлен **теневой
расчёт**, который ничего не меняет на котле, а только логируется и шлётся в
Telegram для анализа и подбора коэффициентов:

```
correction = Kp × rawMinDelta + Ki × integral(rawMinDelta, время)
```

- `rawMinDelta` — отклонение **до** применения ступенчатой эскалации (честное
  сравнение с боевой логикой).
- `integral` (`global.heatingIntegral`) — накопленная сумма отклонения по
  времени (°C·ч), с тремя защитами от «перекрутки» (антивиндап):
  - сброс в 0 при попадании в мёртвую зону (`-0.2…0.2`);
  - жёсткий клэмп на `±3` °C·ч (`INTEGRAL_LIMIT`);
  - ограничение `dtHours` максимум 1 часом — защита от аномально большого `dt`
    после простоя/перезагрузки хаба.
- `Kp` переиспользует ту же логику, что и боевой `correctionFactor` (2/2.5/3 по
  величине отклонения).
- `Ki = 1.5` — стартовое значение, подбирается по накопленным данным.

Результат попадает в каждое Telegram-сообщение отдельной строкой:
```
🧪 PI-тест (не управляет котлом): Δ=-0.2°C, интеграл=0.00, рекомендация=47°C
```

**План внедрения:**
1. *(текущий этап)* Копим сообщения в Telegram вживую, параллельно с боевой логикой.
2. По накопленным данным подбираем `Ki` и `INTEGRAL_LIMIT` — смотрим, не упирается
   ли интеграл в лимит слишком часто, и совпадает ли рекомендация ПИ по
   направлению/величине с тем, что реально помогало прогреть комнаты.
3. При удовлетворительных результатах — переключаем `newWaterTemp` на формулу ПИ,
   ступенчатую эскалацию убираем или оставляем закомментированной как fallback.

## Известные ограничения

- В двух местах (`Hub недоступен` и `Не удалось определить самую холодную
  комнату`) код вызывает `global.sendToTelegram(...)`, которой в файле не
  существует — есть только `sendTG(...)`. Эти ветки отрабатывают редко (Hub
  недоступен практически никогда не случается в рантайме; "нет ни одной
  комнаты" тоже не должно происходить, так как `getColdestRoom` всегда
  возвращает хотя бы одну комнату, если список комнат не пуст), поэтому баг
  пока не проявлялся на практике, но при реальном срабатывании этих веток
  сообщение в Telegram не уйдёт — нужно будет заменить вызов на `sendTG`.
- Антивиндап-параметры ПИ-регулятора (`Ki`, `INTEGRAL_LIMIT`) — временные,
  подобраны "на глаз", требуют калибровки по реальным данным (см. раздел выше).
- Качество воздуха для "Кухня 🍽️" — это TVOC (ppb), а не CO₂ (ppm), как у
  остальных комнат — другой тип датчика на месте установки.
